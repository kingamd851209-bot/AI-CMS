# 60 — 串行切站并保护签收回执编辑

**审查编号** C2、C3

**优先级** P2

**状态** 已通过真实浏览器、会话及签收回执回读

## 问题与依据

快速切站重入会让上下文和权限收到迟到写回，服务端会话也按处理顺序更新。签收回执编辑或保存期间切站、切部署会重置弹窗。见 `admin-ui/src/stores/siteContext.ts:844`、`cms-core/src/main/java/com/xinhongru/site/context/SiteContextService.java:81`、`admin-ui/src/components/sites/WorkbenchReleaseReview.vue:321`、`admin-ui/src/views/sites/SiteBuildWorkbenchView.vue:2966`。

## 修改范围

- 通过现有站点上下文统一串行提交会话选站。切站及权限刷新写回前核对仍适用的选择和站点，失败时以服务端实际会话重读状态。
- 将签收回执编辑态和保存态接入工作台统一离开保护，覆盖导航、切站及切部署。保存完成后按发起时的站点和部署范围反馈结果，允许原范围回读已提交回执。

## 回归验收

- [x] 普通管理员连续切换三个权限范围不同的站点，模拟前一次请求或权限刷新延迟及切站失败。最终页面、权限、会话选站与后续接口写入范围一致。
- [x] 在 CMS 托管及独立托管分别编辑签收回执，触发切站、切部署或离开。取消离开后保留输入，确认放弃后切换成功。
- [x] 延迟保存应答并尝试离开，验证结果可见，重回原范围可读到提交回执，目标范围无串写。

留证保存网络时序、会话选站及回执回读。依赖现有站点上下文和工作台离开保护，可独立实施。

## 2026-11-27 验证记录

本机 Node 使用实际 Pinia store 和 HTTP 替身验证了三个站点的选站链。站点 2 权限读取延迟时，站点 3 的提交尚未发起。释放应答后顺序为 `POST 2 → GET 2 → POST 3 → GET 3`，界面站点、权限组和替身会话均指向站点 3。故意拒绝下一次切站后，读取当前会话，三者仍一致。签收回执的实际浏览器点选、保存延迟及原站回读待核。

本机 Node 还执行了签收组件的 `save`、`changeDeployment` 以及工作台的 `confirmReleaseLeave`。取消切站或切部署后原表单文本仍在。刻意延迟保存响应时离开和切部署均被阻止。返回成功后，反馈仍关联发起保存时的 CMS 部署及包版本。确认放弃后可切换部署。请求与事件使用替身，真实界面及数据库回读尚待核对。
