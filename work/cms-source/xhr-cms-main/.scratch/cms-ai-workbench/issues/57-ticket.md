## 实施边界

抽屉载入与提交携带版本标识，复用现有锁内冲突校验。发生冲突时保留当前编辑者的未保存输入，提示重读最新版后再提交。检查新增记录、旧调用方、字段校验和非抽屉入口的兼容。前后端配套回退，回退前核对 API 响应形状对旧客户端的影响。

## 验收

- [x] 两名编辑打开同一条记录，分别更新标题与封面，后提交旧表单收到冲突提示，首位编辑的修改保留。
- [x] 正常重读并提交后，后台同时回读两项修改；验证新建、无冲突保存及原本可用的旧调用方式。
- [x] 留存两个会话的请求版本、冲突响应和最终记录值，无需发布到独立站。

可独立实施。复用该保存服务已有的版本冲突约定。

## 本轮实施与验证

原生内容抽屉读回并提交记录版本，服务在锁定当前记录后比较版本。发现冲突时返回 409，保留抽屉表单。新建与复制使用新记录入口，旧 API 调用方可继续省略版本。

Windows JDK 21 的 CMS 站点和管理端依赖编译通过。定向测试覆盖过期版本拦截、拦截时无写入和最新版本可保存。实际双会话、前端构建及正式操作入口核验由统一验证记录承接。
## 双会话实测

本机隔离站由两名不同的合成管理员分别登录 Chrome 独立会话。两人从内容管理抽屉打开同一记录，均读到版本 5710:3。第一位修改标题保存成功，第二位从旧版本保存封面收到 HTTP 409，输入框仍保留拟保存的地址；此时服务端保留新标题和原封面。重新打开后读取 5710:4，再次提交返回 200，最终版本 5710:5 同时包含新标题和新封面。随后用原 API 省略版本新建记录，再以旧调用形状更新，正常读回。详见[脱敏回执](<D:/CodexBuilds/cms-workbench/remaining-437f76a5/57-ui.json>)。
